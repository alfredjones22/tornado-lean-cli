# Native sequential deposit invoice route

[`DepositSend.lean`](../Tornado/Cli/DepositSend.lean) implements one public Classic invoice. Explicit `--dry-run` derives the payer address through the native signer, checks the selected chain, pool denomination, balances, and ERC-20 allowance, then prints the exact reset, approval, and deposit calls. It does not sign or submit. `--key-file` selects a protected raw key file; omitting it opens a hidden controlling-terminal prompt without creating a key file.

The `--broadcast [--journal <new-path>]` route can sign and broadcast native EIP-1559 transactions. Run `--dry-run` first. By default, the user must type `SEND` after seeing each transaction's target, calldata, value, nonce, gas, fee cap, and maximum gas cost in wei and ETH. Explicit `--non-interactive` skips that confirmation and requires a protected `--key-file`; it still prints each review and preserves all validation, fee bounds, revalidation, journaling, reservations and uncertain-outcome stops. It does not enable broadcasting by itself, and `--yes` remains unavailable. The route refuses a sender with an existing pending nonce. It checks token balance and allowance before deposit, and checks the ETH balance against the maximum gas cost. The quoted maximum gas cost remains capped at 0.02 ETH per transaction. ETH deposits greater than 0.01 ETH also retain the 10% value cap; deposits at or below 0.01 ETH use only the absolute cap. Gas is capped at two million units including 20% estimation headroom. Classic deposits can exceed one million gas even at ordinary fees. These limits can still reject a legitimate transaction during high fees.

Omitting `--journal` chooses `tornado-deposit-<chainId>-<32 hex characters>.json` in the current directory, with a fresh 128-bit OS-random name. The chosen path is printed and the adapter creates it exclusively with private permissions. Dry-run creates none. Existing claims and sender locks still block duplicate attempts regardless of the chosen journal name.

Before signing, the route exclusively creates a per-sender lock and a permanent per-invoice claim next to the protected key file (or beside the journal for interactive entry), then creates a new protected journal. The claim binds chain, pool, and commitment and prevents a second attempt with another journal path while the same reservation directory is used. After signing, an exact transaction hash is durably recorded as `prepared` before signed bytes reach `eth_sendRawTransaction`. An exception or wrong returned hash stops; there is no automatic retry. Subsequent steps wait for the prior exact successful receipt and Deposit event or approval allowance. The RPC transaction, receipt, and containing block are checked for one validated inclusion, including the same block hash and receipt location; there is no further block-depth wait. A failure leaves the sender lock and claim for manual reconciliation. A successful run releases the sender lock by exact-content removal; the claim remains. `deposit status` can read the journal, but the journal does not pin the sending RPC URL, so supply `--rpc` when reconciling through a custom endpoint.

Existing-file errors name the sender lock, commitment claim, or journal and its path. They preserve the existing file and explain reconciliation; a file conflict is not evidence that a reservation is stale. Permanent commitment claims remain after successful deposits. Do not clear all Tornado dotfiles to bypass this protection.

The compiled `deposit_send_test` covers ETH and USDC planning, wrong chain/denomination/balance, a failed journal write before send, one ambiguous send with retained prepared hash, pending-nonce and excessive-fee rejection, a stopped inclusion-validation fault, and exact Deposit-event confirmation. Fee regressions include a 0.01 ETH note with a 1,156,615 gas estimate, buffered to 1,387,939, at a 1 gwei fee cap (0.001387939 ETH maximum cost): it passes despite exceeding the old 10% limit. A 0.1 ETH note remains subject to 10%, and the 0.02 ETH absolute ceiling still stops a small deposit. The separate `native_signer_test` compares the protected C signer with the pure Lean and pinned viem vectors. These are offline checks, not a live funded test.

## Secret handling

The live invoice route passes only a protected key-file path or public command-local interactive source alias, plus a public transaction digest, into its C signer. File input is checked and bounded to 1,024 bytes; hidden terminal input is also bounded and never becomes a Lean value. The signer uses locked native memory, randomizes a pinned libsecp256k1 context with OS entropy, and returns only the uncompressed public key and verified recoverable signature. Lean derives the Ethereum address, requires it to match the reviewed sender after approval, and serializes and checks the exact transaction before journaling and broadcast. The C boundary sets process core-dump limits to zero, clears its temporary secret page, and rejects any failed memory-control, entropy, key, signature, or recovery check. Interactive sessions are cleared on normal completion or failure. This reduces key exposure; libsecp256k1, the compiler, OS, C wrapper, and Lean integration remain trusted, and complete erasure or whole-route side-channel safety is not proved.

The `deposit send` and `withdraw batch` dry runs use the same C boundary to derive public owner addresses from protected files or hidden entry, without loading those keys into Lean. Note creation, backup inspection, and the isolated withdrawal prover use Lean-managed note secrets and Strings. A byte-only Lean key parser is a compatibility reference and is not used by these command routes. Note-bearing types do not derive debug `Repr`, and an invalid BIP39 word produces a fixed error rather than echoing it. The generic private-file binding clears buffers on failed reads and comparisons. These controls do not establish whole-CLI secret safety.

## Production limits

- The pinned libsecp256k1 signer is a stronger secret boundary than the pure Lean `Nat` signer, but neither the complete invoice route nor its C/OS/compiler boundary has an independent security audit. Separate [Sepolia ETH execution results](SEPOLIA_LIVE_TESTS.md) include one public-invoice deposit; they do not establish production safety or ERC-20 invoice coverage. The route remains experimental.
- An unknown outcome must be reconciled before clearing a sender lock or reusing the key. A stale claim can be cleared only after checking the journal and chain; a copied key in another directory is outside this local claim boundary.
- One validated inclusion does not prevent a later reorg or prove finality. A malicious RPC can fabricate consistent chain data. HTTPS authenticates the configured server, not Ethereum consensus.
- Public invoices do not prove the intended recipient retained the note secret. The payer should confirm that through a trusted channel.
- Multi-note `deposit send` batching and a shared sequential journal are outside this route.
