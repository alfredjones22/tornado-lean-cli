# Native sequential deposit invoice route

[`DepositSend.lean`](../Tornado/Cli/DepositSend.lean) implements one public Classic invoice. Explicit `--dry-run` reads a protected key file to derive the payer address, checks the selected chain, pool denomination, balances, and ERC-20 allowance, then prints the exact reset, approval, and deposit calls. It does not sign or submit.

The `--experimental-send --journal <new-path>` route can sign and broadcast native EIP-1559 transactions. It does not accept `--yes`: the user must type `SEND` after seeing each transaction's target, calldata, value, nonce, gas, fee cap, and maximum gas cost in wei and ETH. The route refuses a sender with an existing pending nonce. It checks token balance and allowance before deposit, and checks the ETH balance against the maximum gas cost. The quoted maximum gas cost is capped at 0.02 ETH per transaction, and ETH deposits are also capped at 10% of their value; gas is capped at one million units. These conservative limits can reject a legitimate transaction during high fees.

Before signing, the route exclusively creates a per-sender lock and a permanent per-invoice claim next to the protected key file, then creates a new protected journal. The claim binds chain, pool, and commitment and prevents a second attempt with another journal path while the same key directory is used. After signing, an exact transaction hash is durably recorded as `prepared` before signed bytes reach `eth_sendRawTransaction`. An exception or wrong returned hash stops; there is no automatic retry. Subsequent steps wait for the prior exact successful receipt and Deposit event or approval allowance, and for 12 numbered-chain confirmations with the same block hash and receipt location. A failure leaves the sender lock and claim for manual reconciliation. A successful run releases the sender lock by exact-content removal; the claim remains. `deposit status` can read the journal, but the journal does not pin the sending RPC URL, so supply `--rpc` when reconciling through a custom endpoint.

The compiled `deposit_send_test` covers ETH and USDC planning, wrong chain/denomination/balance, a failed journal write before send, one ambiguous send with retained prepared hash, pending-nonce and excessive-fee rejection, a stopped confirmation-depth fault, and exact Deposit-event confirmation. The separate `native_signer_test` compares the protected C signer with the pure Lean and pinned viem vectors. These are offline checks, not a live funded test.

## Secret handling

The live invoice route passes only the protected key-file path and a public transaction digest into its C signer. The signer checks the private file, reads at most 1,024 bytes into a locked native page, randomizes a pinned libsecp256k1 context with OS entropy, and returns only the uncompressed public key and verified recoverable signature. Lean derives the Ethereum address, requires it to match the reviewed sender after each `SEND`, and serializes and checks the exact transaction before journaling and broadcast. The C boundary sets process core-dump limits to zero, clears its temporary secret page, and rejects any failed memory-control, entropy, key, signature, or recovery check. This reduces key exposure; libsecp256k1, the compiler, OS, C wrapper, and Lean integration remain trusted, and complete erasure or whole-route side-channel safety is not proved.

The `deposit send` and `withdraw batch` dry runs use the same C boundary to derive public owner addresses from protected key files, without loading those keys into Lean. Note creation, backup inspection, and the isolated withdrawal prover use Lean-managed note secrets and Strings. A byte-only Lean key parser is a compatibility reference and is not used by these command routes. Note-bearing types do not derive debug `Repr`, and an invalid BIP39 word produces a fixed error rather than echoing it. The generic private-file binding clears buffers on failed reads and comparisons. These controls do not establish whole-CLI secret safety.

## Production limits

- The pinned libsecp256k1 signer is a stronger secret boundary than the pure Lean `Nat` signer, but neither the complete invoice route nor its C/OS/compiler boundary has an independent security audit or funded test. The route remains experimental.
- An unknown outcome must be reconciled before clearing a sender lock or reusing the key. A stale claim can be cleared only after checking the journal and chain; a copied key in another directory is outside this local claim boundary.
- Twelve confirmations reduce shallow reorg risk but do not prove finality. A malicious RPC can fabricate consistent chain data. HTTPS authenticates the configured server, not Ethereum consensus.
- Public invoices do not prove the intended recipient retained the note secret. The payer should confirm that through a trusted channel.
- Multi-note `deposit send` batching and a shared sequential journal are outside this route.
