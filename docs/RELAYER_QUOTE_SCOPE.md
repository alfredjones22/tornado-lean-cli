# Native Classic relayer withdrawal boundary

`Cli/RelayerSend.lean` implements discovery, status and fee preparation plus an experimental, one-POST submission executor. `Cli/RelayerWithdraw.lean` connects those checks to the separate native Lean prover worker, public history session, typed approval and protected note claim. The prover is variable-time and does not guarantee secure erasure. Tests use public unfunded fixtures and inject all submission effects; they do not submit a withdrawal.

The module uses the pinned mainnet/Sepolia registry deployment blocks, aggregator addresses and ENS subdomains. It scans only the pinned registry's `RelayerRegistered` event, checks canonical event ABI bytes and ASCII ENS namehash, deduplicates registered names by newest event position, and reads each candidate's current aggregator record at the captured block. A candidate needs a matching reward owner, current registration, at least 40 TORN of stake, and the relevant hostname record. The status endpoint must be an HTTPS DNS origin without credentials, path, query, fragment, port, local suffix or numeric IP. This is deliberately narrower than the TypeScript URL parser; unsupported Unicode ENS names are rejected rather than incompletely normalized.

Status validation checks the selected original pool, network, queue length from zero through five, nonzero matching reward account, bounded version string, and a service fee of at least 0.01% and below 1%. The percentage is parsed as an exact JSON decimal and rounded to basis points without floating-point arithmetic. The fee uses the pinned SDK estimate of `gasPrice * 550000`, plus the service fee. A host gas price above 1,000 gwei is rejected, and the total fee must be positive, below the note value, and no more than 20% of the note.

ERC-20 quotes convert the network component using the relayer's token price and require a separate response from the pinned paymaster's `quoteWeiInToken` call at the captured block. The converted network fee may be no more than 20% above that reference. Requiring this reference is stronger than the alpha.38 SDK fallback that permits a missing reference. Neither source is authenticated against consensus or deployed bytecode by this module; the check prevents the relayer from supplying both prices unilaterally under the stated RPC/code assumptions.

Before submission, `recheckWith` checks the quote's five-minute lifetime and rereads registration, stake, endpoint, reward and service fee. The private `Quote` constructor means normal callers obtain quotes through checked preparation. `prepareProof` verifies the worker result with the compiled Classic verifying key and binds all six public inputs, selected pool, registered reward and reviewed fee. The native adapter builds those inputs from a checked selected-pool history session. Immediately before reserving the attempt it rechecks the captured block's canonical hash, selected root membership, unspent nullifier, chain and current count through exact-block RPC calls. Those calls remain provider claims under the RPC trust assumption.

Native proving has its own bounded worker deadline and may exceed five minutes. After proof generation, `refreshPreparedWith` rereads current registration, status, gas price and any token oracle reference, requiring the exact original reward, endpoint, service rate and every fee amount to remain unchanged. It preserves the proof, six inputs and POST body byte-for-byte, then starts a fresh five-minute review window. A changed fee, endpoint, reward or policy requires new preparation before any proof exposure, transaction attempt or on-chain charge. Gas-price changes during slow proving can therefore prevent completion even for an otherwise valid note; this conservative availability limit remains, rather than silently changing the proof-bound fee. The refresh avoids consuming the entire review window inside a slow prover while preserving proof-bound values.

Resource bounds include a 1 MiB RPC result, 64 KiB status result, 64 MiB aggregate replies, 8,192 total requests, a five-minute operation deadline, 4,096 registry log requests with bounded range splitting, 2,048 registry events, 256 ENS names and 64 liveness checks. An incomplete or malformed result is rejected. A valid registration may be missed when providers omit events; the module cannot prove endpoint completeness, stake truth, Ethereum finality, DNS integrity, or the cryptographic properties of ENS Keccak.

The offline `tests/RelayerSend.lean` suite compares namehash, both supported aggregator call shapes, registry events and aggregator response bytes with `viem@2.55.19`. It exercises range splitting and rejects wrong emitters, removed logs, malformed registration ABI, insufficient stake, reward/network changes, excessive queue/service/total fees, token price deviation, missing oracle data and expired quotes. It makes no network request and uses no funded note.

Submission requires `--experimental-send` and typed `WITHDRAW` approval. `--yes` and `--retry-rejected` are unavailable for this route. Before the exact proof body leaves the parent process, exclusive protected creation of the same opaque per-note filename used by the 4337 routes records the RPC, pool, nullifier, recipient, reward, fee, exact public args, and hashes of the proof, calldata, request and POST body. It does not persist the note, secret preimage or executable proof. An existing claim blocks a second submission, including after a lost reply. Later writes preserve all immutable bindings and known job/transaction IDs through protected byte-for-byte CAS. A failed or ambiguous write never deletes the original claim or authorizes a retry.

There is one proof-bearing POST and no POST retry loop. Lost replies, invalid job IDs, timeouts and endpoint failure preserve an unknown attempt. A returned job ID only provides a status hint. Existing `RelayerWithdrawalStatus` establishes success only from matching pool event and successful transaction receipt with the exact nullifier, recipient, reward and fee. Bounded polling also permits recovery from chain evidence when no job ID was received. Status reconciliation remains available after the command exits. Neither confirmation nor any other local state automatically releases the permanent note claim.

`tests/RelayerSubmit.lean` checks a native-verified public proof, altered recipient/reward/coordinates, approval/history/reservation ordering, duplicate claim rejection, lost and malformed replies, job-only claims, incorrect recipient events, persistence failures, immutable journal bindings and concurrent CAS conflicts. Its proof fixture is generated from public witness data with every pinned R1CS constraint rechecked. These execution tests complement the Lean lemmas; they are not a full refinement proof of the effectful command.
